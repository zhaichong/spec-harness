# 前后端契约规则

当任务改变或需要明确双方共享的 API、事件、字段、权限或错误语义时应用。优先沿用项目已有 OpenAPI、DTO、接口文档或契约测试方式；没有现成机制时，在简短 Spec 中记录必要字段与语义即可。仅同时改动前后端且契约不变时，不因此增加文档。

## 先固定契约

- 方法、路径、认证方式和权限范围。
- 请求字段的名称、类型、必填、默认值和边界。
- 响应字段、空值、枚举、分页和排序规则。
- 时间格式及时区、金额精度和标识符类型。
- 错误状态、业务错误码以及前端对应行为。
- 新旧客户端和服务端的兼容、发布顺序及回滚要求。

需求仍在变化时只固定当前实现需要的契约，不为未来场景提前设计通用协议。

## 实施顺序

1. 在已有契约来源或简短 Spec 记录改变的契约及可观察验收，不重复建立同内容表格。
2. 后端保证校验、鉴权、业务结果和错误语义可验证。
3. 前端按同一契约处理成功、失败、加载和空数据状态。
4. Mock 符合正式契约；替换真实接口时删除或隔离临时路径。
5. 任一端改变共享语义时同步更新 Spec，定位受影响调用方、类型及测试并补充验证。只复查差量；已有实施授权有效时继续，仅实质未决的业务、兼容性或授权问题需询问。

实现顺序可按项目情况调整，但不能让两端各自猜测契约。

## 最小验证

- 对照契约检查字段、类型、空值、枚举和错误。
- 验证一条端到端主路径和一个关键失败路径。
- 验证未授权或越权请求不会仅由前端拦截。
- 检查前后端版本错配时的兼容行为。
- 数据库或外部系统参与时，补充数据对账或副作用证据。

简短 Spec 用自然语言记录验收即可；完整追踪统一用 `AC-01` 等数字编号，领域写在描述中。

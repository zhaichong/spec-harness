# 增量处理需求变更

新消息与当前目标合并；只有用户明确替换目标才替换。目标或预期结果无法从上下文确定时先问关键问题，能从仓库查明的实现细节自行查明。

1. 定位改变的验收点、代码、调用方与验证，考虑共享依赖和端到端影响。
2. 只更新受影响部分。受影响任务重新打开，撤销过期的完成结论；保留仍适用的设计和证据，不重做整套流程。
3. 重新验证改变的行为及相关回归。代码、依赖、配置或环境变化使旧证据失效时扩大检查；无法确认适用性则重验。
4. 新增风险时按主流程重新判断复查和实际操作授权；旧授权不涵盖新范围时才补充。

Fast 在聊天中说明差量即可。简短 Spec 更新已有记录，必要时留一句“变化 → 影响 → 重验或复用依据”；不因一次修改创建任务文件、报告或新版本目录。

已启用完整追踪时保留 AC 和任务编号，新项用新编号，删除/替代项移出当前映射并留说明。只对业务、契约、范围、验收或风险实质变化升版；不重复申请同范围授权。受影响验收标 partial 或待验证，进度只维护 tasks.md，证据和复用说明只维护检查报告。

例如：只调整按钮文案且未影响交互和依赖，可继续使用后端证据；共享配置影响多个模块时，即使需求只有一句话，也需验证相关路径。

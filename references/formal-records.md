# 完整追踪记录（按需启用）

只在用户、项目明确要求结构化追踪，或长期多阶段任务确需自动核对任务与验收映射时读取。普通 Fast 和简短 Spec 不使用本文件的模板及脚本。用户已有的实施授权持续有效；结构校验只验证记录和映射，不证明授权真实、测试执行或审核独立。

## 最小产物

在项目根或用户指定目录的 `.spec/<YYYY-MM-DD>-<简述>/` 建立；同一任务复用，不覆盖别的任务。默认不提交 `.spec/`，不修改仓库 ignore，也不默认切分支。

- [spec.md](../templates/spec.md)：当前需求、约束、AC、风险、实施授权及自审发现。
- [tasks.md](../templates/tasks.md)：唯一进度；每个当前 AC 至少由一个 `[required]` 任务覆盖。
- [check_reports/harness-check.md](../templates/harness-check.md) 与 `evidence/`：实际检查和验收证据。
- [plan.md](../templates/plan.md)：仅加码或确有多方案取舍时。
- [session/independent-review.md](../templates/independent-review.md) 与 [session/log.md](../templates/session-log.md)：加码时。

普通自审合并到 Spec 的「审核发现」，以反方视角检查假设、失败路径和验收是否成立，只记录发现及处理结果。需要展开时可用 [session/adversarial-review.md](../templates/adversarial-review.md)；交付复查可用 [check_reports/delivery-review.md](../templates/delivery-review.md)。这两份文件不强制创建；已存在则保持结论与当前版本一致，不复制重复报告。

Spec 的「审核状态」只填明确状态：`自审通过`、`对抗自审通过`、`独立复查通过`、`待澄清` 或 `阻塞`；独立复查、对抗自审和交付复查报告的结论字段只填 `通过` 或 `阻塞`，解释放在发现与处理。交付必须是已通过状态，旧稿的 `fresh review` / `人工复查` 仍检查对应独立审核记录。旧状态若只写「未独立」，需补充实际自审结论，不必重新申请实施授权。

## 验收与风险

使用 `AC-01` 等稳定编号，写可观察结果、风险与证据类型。业务、契约或风险实质变化时升版；排版、实现细节或日志更新不单独升版。版本字段只写 `v1` 等版本号。

变更面逐项写「是」或「否」，指本次改变或实际操作涉及的行为，不因项目本来有登录或数据库就标风险。数据写入/删除、权限/敏感数据、外部副作用、不可逆、生产或批量为「是」时，映射到关键高风险 AC，例如 `KR-01 [数据写入] → AC-02`，不能仅用人工证据。普通业务写库只标对应写入面，不因此增加独立复查。涉及写入或加码时，明确提交点、重复执行结果、部分失败及禁止结果。

「实施授权」引用用户要求实施的原话或可定位会话，并说明涵盖的范围。只出方案的请求不能填成实施授权。授权范围发生变化时重新判断，必要时补充；不要把「无需确认」本身当作执行任何操作的授权。旧稿的 `Standard` / `Strict` 档位与「作者确认」字段继续兼容；沿用旧确认字段时仍须对应当前版本，更新到新字段时保留真实来源。

## 审查与执行边界

查明仓库事实，解决自审发现后开始相关实施；未决业务规则、兼容性选择或授权问题只阻塞依赖它的部分。普通实现细节由 Agent 按项目约定决定。

加码面为权限/敏感数据、外部副作用、不可逆、生产或批量。高风险部分交付或实际操作前由未参与起草的审核者复查原始需求、Spec 和必要代码，记录来源、输入范围、发现及结论；不得用同一 Agent 的反方自审冒充独立复查。可先做不依赖未决结论的本地实现和隔离测试；缺少审核资源时说明缺口，保留高风险部分的待处理状态。

新增需求只复查受影响部分；独立审核者可在保留既有结论的基础上补充差量审核，记录当前版本、变化及复用依据。不得仅改报告版本号就声称已复查。

开发代码、在隔离测试数据上验证与执行真实操作分别判断。实际共享/外部写入、生产或不可逆操作前，在 session/log.md 记录操作、目标范围、dry-run/预览、已有授权原话、失效条件及不可重复操作；已有授权覆盖当前范围时直接沿用，只有缺失或失效才补充确认。「实际执行」填 `有` 或 `无`：有操作时逐项填写授权表五列；无操作时删除操作表或只保留唯一的「无」行。状态与操作表不能矛盾，说明文字不能代替字段。兼容旧稿独立一行的「无外部副作用」声明，但同样不能与实际操作并存。未经授权不 merge、push、部署或写生产数据。

## 验证与待交付

依主流程选择检查，证据中记录命令/步骤、结果、代码基线及必要环境。每个 AC 在报告中单列一行，并引用任务目录内非空材料（`文件：evidence/...`）；同一次测试输出可被多个 AC 引用，分别说明覆盖的结果。复用证据须说明为何仍适用于当前代码、依赖与环境。

required 任务全部完成，每个当前 AC 为 `pass` 且有证据，自审及必要复查无阻塞，才将 tasks.md 标为待交付。缺少工具或环境导致无法验证时记录缺口，不伪造通过。

实际 AC、任务、审核和授权记录使用模板格式写在正文。单值元数据只保留一处，历史状态变化写在说明中；空任务或验收报告不能通过。AC 统一用 `AC-数字`，不加 FE、BE 等领域前缀。任务编号须唯一，映射只引用当前 AC；optional 无关联项写 `→ 无`。字段缺失或格式错误会报告；代码块只作示例，未闭合代码块也会报错。结构通过仍不能证明真实执行或证据与代码的一致性。

脚本路径相对本 Skill 根目录：

```text
scripts/check_spec.py <.spec/任务目录> --stage draft
scripts/check_spec.py <.spec/任务目录> --stage delivery
```

draft 在设计/审核记录就绪后检查结构，delivery 在待交付前检查任务和证据。也可用 `scripts/check_spec.ps1` 启动。Python 不可用时先寻找已有运行时；仍不可用则说明结构检查未执行，可继续独立工作，不声称检查通过。
